Toy Monte Carlo on HTCondor

In Part 3 we computed the local significance of each peak using Wilks’ theorem. That number, however, does not account for the look-elsewhere effect (LEE): because we searched for a peak anywhere in the 560 MeV wide window, the true global p-value is larger by roughly the number of independent resolution elements in the search range. The standard cure is a Toy Monte Carlo (Toy MC): generate a large number of pseudo-experiments from the pure background hypothesis, run the same fit on each one, and count how often the best-fit of a toy exceeds what we saw in data.

The original analysis quoted 50.5 million toys for peak 1 and 9.8 million for peak 2. On a single core that would take months. This part shows how to run the whole thing in parallel on an HTCondor cluster in a few days of wall time.

Directory Layout

All the condor machinery lives under condor/ inside the project root:

The key design principle is that toymc_worker.py has no ROOT dependency. It only needs numpy and scipy, both of which are available everywhere. The main analysis script (significance.py) is only called once, during setup, to extract the data values. After that, every condor worker is completely independent.

The Worker: toymc_worker.py

Each HTCondor job runs one instance of toymc_worker.py. It receives the data threshold, generates toy pseudo-experiments from the pure three-body phase-space background, fits each toy exactly as described in Part 3, and writes a small JSON file recording how many toys exceeded the threshold.

The toy generation is straightforward: sample values from the phase-space CDF using inverse-transform sampling, then bin them into the same 20 MeV histogram used for the real data.

The fit per toy mirrors Part 3 exactly: null fit (PS only), then a one-peak fit with a coarse mass–width grid scan followed by L-BFGS-B refinement. Only two parameters are allowed to float in the refinement step (the PS normalisation and the signal yield), with mass and width held at the best grid point. This is the key optimisation that reduces per-toy runtime from ~9 minutes (full floating fit) to ~9.5 seconds — a 56× speedup — while still sampling the correct tail of the distribution.

Each worker uses a deterministic seed derived from its job ID:

Peak 1 uses seed_base = 420000000 and peak 2 uses 430000000, so the two sets of toys are statistically independent regardless of job scheduling order. This makes the full result exactly reproducible from the job IDs alone.

Step 5: Final Plots — plot_all.py and plot_toymc_result.py

With both merged_peak1.json and merged_peak2.json in place, run the two plotting scripts:

plot_all.py re-runs the three-hypothesis fits on the real data spectrum (null / one-peak / two-peak), reads the merged Toy Monte Carlo results, and produces figure/dm_spectrum_all_fits.png with the global significance embedded in each panel annotation.

plot_toymc_result.py shows the distribution of best-fit across all Toy Monte Carlo pseudo-experiments on a log-scale y-axis, with a vertical red line at the data value. This is the standard LEE diagnostic plot: if the data line is well into the tail of the toy distribution, the global significance is robust.

Resource Notes

Each job requests 1 CPU and 2 GB RAM. The per-toy runtime is ~9.5 s for peak 1 and ~8.5 s for peak 2. The table below summarises the expected resource usage at the default scale:

Jobs Toys/job Total toys CPU time Wall time (est.)
Peak 1 5000 10000 50 M ~13 000 h ~3 days
Peak 2 1000 10000 10 M ~2 400 h ~12 h

Wall time estimates assume ~600 concurrent cores available. If the cluster is busy, scale down queue first and merge partial results while waiting for the rest to finish — merge.py handles any subset of jobs correctly.
